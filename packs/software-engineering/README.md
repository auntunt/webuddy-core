## Native 条目

19 条。GOAL-2 I2 给探测表达式补了两样东西——第 12 个原语 `applies-if`（能判"不适用"）
和小节指令 `不过时算: fix|ask`（"没过"落成哪一档由门禁说了算）——之后重新盘了一遍
这 20 条，只有 4.9 能在**每一个分支上**都被表达出来，已翻成 DSL 删掉。
剩下 19 条留下来的理由归成三类，没有一条是"懒得翻译"。

**一、光有"不适用"这一种额外答案还不够：这些门禁一条里同时要两种。**

`不过时算` 是门禁级的，一条门禁只能选一档。而下面这几条在同一条判据里既要说
"你做错了"（fail）又要说"你还差一件事"（fix），或者还要再加一个"机器判不了"（ask）。
选哪一档都在说谎：选 fix 会把真违规说轻，选 fail 会把"栏空着"说成"你违规了"。

实测证据（造出真实项目会命中的分支，跑 native 看它答什么）：

| 门禁 | 同一条里的两档 | 实测 |
| --- | --- | --- |
| 8.6 | fail / fix | 变更记录里「测试是否全绿」填了「否」→ fail「1 次发版前测试没全绿就发上去了」；那一栏空着 → fix「空着等于没跑——跑一次填上」 |
| 8.7 | fail / fix | 「是否已备份」填「否」→ fail「改坏了数据就找不回来了」；空着 → fix「空着就当没备份，补填一下」 |
| 8.4 | ask / fail | 台账没有能分类型的那一列 → ask「所以这条判不了」；有那一列且需求被当故障改掉 → fail |

这几条只需要一种额外答案，`applies-if` 或 `不过时算` 本来够用；卡住它们的是数据通道。

### 没能用 DSL 表达的原因（§11.1 要求逐条记）

上面三张表就是这份记录。GOAL-2 I2 之前这份记录归纳成一句话是"缺的不是某个原语，
缺的是第三种返回值"；那句话现在只对了一半，剩下的一半是这次做完才看清的：

- **第三种返回值补上了**。第 12 个原语 `applies-if` 给出 `na`，小节指令
  `不过时算: fix|ask` 给出另外两档。20 条里因此走掉一条（4.9）。
- **补上之后剩下的缺口是两样别的东西**。一是"一条门禁要两种非通过答案"——
  `不过时算` 是门禁级的，选哪一档都在说谎（第一类 3 条）。
  二是数据通道：运行记录、`.git/`、人工确认记录、以及需要跨行/跨表交叉的判断，
  探测表达式都够不着（第二类 14 条）。这两样都不该靠加第 13 个原语解决——
  原语表已满员封版，再有新需求一律降级 human。

第一类要的是让 `不过时算` 能按分支给不同的档（那等于把判定逻辑搬进 probes.md，
探测表达式就不再是"只答事实"了）；第二类要的是一份"包提供事实"的通用协议
（DECISIONS 里 [P3z] 记的选项④），两件都是单独立项的事，不在本期范围内。

### 与 ref 有意不一致的两条

#### 4.9：只在 package.json 的正文里找组件名

ref 的 4.9 取 `Object.keys(f.eng.deps)`（`dependencies` 与 `devDependencies` 两个
对象的键），逐个跟九个"约定方案之外"的组件名比。本包翻成 DSL 之后用的是
`regex-hit("package.json", "\"(react-redux|redux|…)(/[^\"]*)?\"\\s*:")`——
读的是整份 package.json 的正文，不只是那两个对象。

差别在于：如果这九个名字之一出现在 `dependencies` / `devDependencies` 之外的
某个对象里且长得像一个键（例如自定义的 `"graphql": "…"` 配置段），本实现会报，
ref 不会。实测三个 golden 素材加包内两个样板项目上五处判定与 ref 逐条一致
（na/na/pass/pass/pass），另造两个项目分别命中 fix 分支（依赖里放 mongoose）
与 pass 分支（只有 express），两种实现也一致。

换来的是一个 native 名额和一条不再需要 `f.eng` 事实通道的判据。

#### 4.10：缺目录时 ref 判 fix、本实现判 fail

`ref/webuddy-console/src/rules-late.js:218` 在缺目录时返回 `fix`，并把缺的一次列
全（"缺：src/（放代码）、tests/（放测试）、package.json（记依赖和命令）"）；这个包
的 4.10 走 DSL，返回 `fail`，而且只报第一个缺的（`all` 短路，detail 取第一个失败者）。

留着这个差异是权衡的结果：4.10 的 severity 是 `info`，mvp 模式下被静音、不进
`counts`，golden 对拍看不见它；把它翻成 DSL 换来了一个 native 名额，而 native 已经
正好压在硬上限 20 上。对用户来说两者都是"这里要改"，差的是一句方向提示。

实测三个 golden 素材上 ref 均为 `fix`、本实现均为 `fail`，复现命令与影响面记在
仓库根 DECISIONS.md 的同日 4.10 条。

## 自带的两个样板项目

`webuddy pack test packs/software-engineering` 拿这两个项目试一遍整套判据：

- `fixtures/good/` —— 什么都做齐了的项目，81 条现在该管的全过。人工确认预置在
  `.webuddy/records.jsonl`（28 条 human 门禁 + 7.12 一条）；运行痕迹在
  `.webuddy/state.json` 的 notes.runs 里；存档历史存成 `dot-git/`，跑测试时还原成 `.git/`
  （版本管理工具不肯把嵌套的 .git 目录当普通文件收进来）。
- `fixtures/broken/` —— 从 good/ 拷一份、动了四处，该红的 6 条写在 `expected.json` 的
  mustFail 里，多红少红都算这个包判错了。这几条门禁号是在 ref 上跑
  `node ref/webuddy-console/bin/webuddy.js json` 得出来的，不是手填的。
