## Native 条目

20 条，正好压在硬上限上。留下来的理由归成三类，没有一条是"懒得翻译"。

**一、探测表达式只有"过"和"不过"两个出口，这些门禁必须给出第三种答案。**

"还没走到这一步"（不适用）和"走到了但做错了"（不通过）对人的意思完全不同。
压成一个"不通过"，等于把"你还没开始"说成"你做错了"——这是误报，而误报会让人
不再看工具说什么。

| 门禁 | 要的第三种答案 | 压成两态会怎样 |
| --- | --- | --- |
| 4.9 | 还没有组件清单 → 不适用 | 把"还没建清单"说成"清单里有违规的东西" |
| 5.9 | 还没试过能不能跑 → 去做一件事 | 把"没试过"说成"跑不起来" |
| 5.12 | 同上，试了没成才是坏了 | 同上 |
| 7.12 | 还没上线 → 没有正式环境可查 | 把"还没上线"说成"生产数据脏了" |
| 7.21 | 还没上线 → 不适用 | 同上 |
| 8.4 | 还没进运行阶段 → 不适用 | 刚上线的项目会被说成三条不合格 |
| 8.5 | 同上 | 同上 |
| 8.6 | 同上 | 同上 |
| 8.7 | 同上 | 同上 |
| 6.1 | 一次都没跑过 → 待确认 | 把"没跑过"说成"跑失败了" |
| 5.11 | 轮次没开的时候判不了 | 判绿是假绿灯，判红是冤枉人 |

**二、要读的东西不在产物文件里，11 个原语碰不到那个地方。**

原语能读的是 artifacts/ 下的 Markdown、项目里的文件、以及 .webuddy/evidence/。
下面这些要读的是别的通道，DSL 没有入口。

| 门禁 | 要读什么 | 在哪 |
| --- | --- | --- |
| 4.1 | 存档历史有几次、都记了什么 | `.git/`，要跑命令才看得见 |
| 4.2 | 哪些文件被排除在存档之外 | `.gitignore` 的匹配语义，不是有没有这个文件 |
| 4.4 | 组件版本锁没锁 | package.json 里版本号写法（`^4.19.2` vs `4.19.2`） |
| 4.6 | 代码里有没有写死的密码 | 要扫 src/ 下每个 .js 的正文并排掉注释 |
| 6.5 | 测试跑出来的条数 | 运行记录 `notes.runs.test` |
| 6.11 | 八条安全底线的自查结果 | 运行记录 `notes.security` |
| 7.7 | 冷启动、回滚这些跑过没有 | 运行记录 `notes.runs` |

**三、挂在 human 门禁上、只用它的"不通过"分支做前置。**

内核对 human 门禁只采纳 native 的 fail/fix（见 evaluate.js 的 humanPrecheck）。
这两条留着是为了在问人之前先挡一道："文件都还没有，就别浪费人的时间去确认了。"

| 门禁 | 前置挡的是什么 |
| --- | --- |
| 3.5 | 场景卡或功能清单还没有，没得对照 |
| 7.10 | 交接单没有、或者四栏里有空的 |

### 没能用 DSL 表达的原因（§11.1 要求逐条记）

上面三张表就是这份记录。归纳成一句话：**缺的不是某个原语，缺的是第三种返回值。**
第一类 11 条全是同一个原因——探测表达式返回 `pass|fail` 两态，而这些门禁的正确
答案是 `na` / `fix` / `ask`。加任何一个新原语都解决不了，因为问题在返回类型上，
不在判断能力上。第二类 7 条是数据通道问题：要么得跑外部命令（git、测试），要么
得读运行记录，这两样都不该让探测表达式碰——探测表达式必须是纯的、可重跑的。

所以第 12 个原语的空位继续留空。真要用它的时候，理由应该长得像"有一类判断，
用现有 11 个原语组合不出来"，而不是上面这两种。

### 与 ref 有意不一致的一条：4.10

`ref/webuddy-console/src/rules-late.js:218` 在缺目录时返回 `fix`，并把缺的一次列
全（"缺：src/（放代码）、tests/（放测试）、package.json（记依赖和命令）"）；这个包
的 4.10 走 DSL，返回 `fail`，而且只报第一个缺的（`all` 短路，detail 取第一个失败者）。

留着这个差异是权衡的结果：4.10 的 severity 是 `info`，mvp 模式下被静音、不进
`counts`，golden 对拍看不见它；把它翻成 DSL 换来了一个 native 名额，而 native 已经
正好压在硬上限 20 上。对用户来说两者都是"这里要改"，差的是一句方向提示。

实测三个 golden 素材上 ref 均为 `fix`、本实现均为 `fail`，复现命令与影响面记在
仓库根 DECISIONS.md 的同日 4.10 条。

## 自带的两个样板项目

`webuddy pack test packs/software-engineering` 拿这两个项目试一遍整套判据：

- `fixtures/good/` —— 什么都做齐了的项目，81 条现在该管的全过。人工确认预置在
  `.webuddy/records.jsonl`（28 条 human 门禁 + 7.12 一条）；运行痕迹在
  `.webuddy/state.json` 的 notes.runs 里；存档历史存成 `dot-git/`，跑测试时还原成 `.git/`
  （版本管理工具不肯把嵌套的 .git 目录当普通文件收进来）。
- `fixtures/broken/` —— 从 good/ 拷一份、动了四处，该红的 6 条写在 `expected.json` 的
  mustFail 里，多红少红都算这个包判错了。这几条门禁号是在 ref 上跑
  `node ref/webuddy-console/bin/webuddy.js json` 得出来的，不是手填的。
